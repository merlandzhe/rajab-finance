# Безопасность и ограничения MVP

## Реализовано

- Проверка Supabase Auth через серверный getUser; cookies не принимаются как доказательство роли.
- RLS на каждой публичной бизнес-таблице; anon без доступа к данным/командам. Исключение — узкий RPC с публичными параметрами тарифа.
- Проверки роли и membership в RPC; составные FK tenant/entity; platform admin не получает автоматического доступа к клиентам.
- API проверяет сессию, Zod, Origin, размер тела и постоянные лимиты запросов в БД.
- Авторизация выполняется и на страницах, и на API. Проверка на layout не является единственной защитой.
- Только server env для service role, Telegram, cron; модули интеграций помечены server-only.
- Service role используется только для лимитов, публичного intake, контролируемой загрузки и worker. Обычные команды сотрудника выполняются с его JWT.
- Договоры, версии, графики, платежи, распределения, закупки, файлы и аудит защищены от перезаписи триггерами/правами.
- Idempotency и транзакции, отмена отдельной операцией, блокировка перерасхода кассы.
- Приватный Storage, проверки размера и содержимого файла, UUID-пути; скачивание через авторизацию, attachment, nosniff.
- Noindex, защита от iframe, ограничение источников ресурсов CSP и запрет произвольных HTML-вставок.

## Что не следует считать завершённым

Это локально проверенный MVP, не независимый аудит безопасности и не готовый регуляторный контур.

- Облачные Supabase Auth/JWT refresh/Storage и RLS с реальными проектами требуют staging-проверки. PGlite проверяет SQL, но не инфраструктуру Supabase.
- Браузерные E2E/доступность/визуальный QA всех размеров в этой среде не выполнены.
- Загрузки не проходят антивирус. PDF скачивается как вложение и не показывается inline. Перед допуском реальных чужих файлов нужен антивирус/карантин, лимиты хранилища, жизненный цикл удаления orphan objects.
- CSP пока допускает inline-скрипты Next.js и стили. Перед внешним запуском перейти на nonce-based CSP, проверить сторонние политики и MFA для сотрудников.
- Текущие лимиты IP доверяют только заголовку Vercel. При самостоятельном хостинге требуется доверенный reverse proxy; сейчас такие запросы используют общий local bucket.
- `app_state` возвращает весь доступный реестр. Для больших компаний нужны пагинация и агрегированные серверные отчёты.
- Добавление/отключение сотрудников, создание организаций/подписок и привязка клиента к Auth — операции оператора, не пользовательский UI.
- Нет полного/частичного товарного возврата или изменения цены договора. Поддержана полная отмена ошибочного поступления с причиной; частичная корректировка = отмена + правильная новая запись. Юридические изменения договора не реализованы.
- Передача фиксируется датой и текстовым основанием. Электронная подпись/подписанный акт и проверка права собственности человеком требуют отдельного процесса.
- Нет CSV/XLSX, автоматической фискализации, биллинга SaaS, банковского подтверждения или онлайн-оплаты.

## Секреты и инциденты

Секреты не коммитить и не отправлять в сообщения. При компрометации service role / Bot token немедленно перевыпустить, отозвать сессии при необходимости, проверить аудит и очередь. Передача токена Telegram идёт только сервером в Bot API; ошибки не логируют URL с токеном.

## Telegram

Уведомления не содержат ФИО, телефона или паспортных сведений — только тип события и номер/ID. Доставка at-least-once: если Telegram принял сообщение, а запись статуса не сохранилась, возможен дубль при повторе. Финансовые операции при этом остаются идемпотентными. Нужны мониторинг failed и выбор периода уведомлений до запуска.
