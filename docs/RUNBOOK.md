# Запуск, внешние проверки и восстановление

## Перед подключением внешних аккаунтов

Проект не опубликован. Создание удалённого репозитория/проектов и размещение реальных данных согласовать с владельцем. Сначала закрытый staging с синтетическими данными. GitHub и Vercel нужны для хранения кода/сборки/хостинга; Supabase — Auth/PostgreSQL/Storage. Sites hosting не используется: выбран исходный стек пользователя Next.js/Vercel.

## Подготовка GitHub

1. Создать новый приватный репозиторий; не использовать предыдущий сайт.
2. Восстановить Git из bundle или открыть рабочую копию. Добавить origin и отправить main после разрешения.
3. Включить защиту main и обязательный CI. Workflow не публикует сайт автоматически.
4. Проверить, что `.env.local`, `.demo`, ключи, реальные документы и test-results отсутствуют в Git.

## Supabase staging

1. Создать отдельный проект, выбрать регион/схему размещения после правовой проверки. Не использовать базу футбольного проекта.
2. Применить 001_core.sql, 002_commands.sql, 003_api_storage.sql по порядку от административной роли. Схему private не добавлять в exposed schemas.
3. Создать пользователя Owner средствами Supabase Auth. Выключить общедоступную регистрацию. Не хранить роль в редактируемом user_metadata.
4. Подставить проверенный UUID Owner в bootstrap.sql. Тарифы bootstrap остаются демонстрационными.
5. Создать тестовых Manager, Cashier, Client, владельца второй организации. Внести profiles/membership административным процессом. Для клиента установить customers.auth_user_id; никогда не связывать клиентскую запись по одному введённому телефону без проверки личности.
6. Настроить URL и publishable key, серверный service role, PUBLIC_TENANT_ID. Все ключи service/Telegram/cron — только server env.
7. Использовать DEMO_MODE=false, ALLOW_REAL_INTAKE=false, APP_ORIGIN точно равный origin staging. Auth redirect/site URLs только разрешённые; HTTPS.

## Матрица облачной приёмки — обязательна перед запуском

- Owner: вход, refresh, logout, истёкший/отозванный токен; отсутствие cookie -> 401/redirect.
- Manager: создать клиента/заявку/закупку/договор; изменение тарифов/кассовая операция -> 403.
- Cashier: зарегистрировать разрешённый платёж; доступ к заявкам/загрузке -> 403.
- Client: только свои договоры/платежи/PDF; чужой UUID -> пусто/404, любые изменения -> 403.
- Другая организация: список и прямые PostgREST/RPC/Storage запросы не раскрывают tenant A.
- Platform admin без membership: только метаданные, клиентские таблицы пусты.
- Storage: анонимная ссылка/чужой пользователь не скачивает чек. Прямой upload в обход API запрещён. Файлы >5 МБ, HTML/SVG, активные PDF и повреждённые изображения отклоняются.
- Договор без закупки или без окончательного согласования не создаётся. Попытка переписать цену/график блокируется.
- Два параллельных одинаковых платежа создают одну операцию; два разных запроса на остаток не создают переплату.
- Полная оплата не закрывает договор до передачи; после оплаты и передачи статус closed.
- Отмена сохраняет исходный платёж, восстанавливает задолженность и уменьшает кассу. Нехватка кассы запрещает отмену.
- Desktop/phone E2E и ручная проверка Safari iOS, клавиатуры, тёмной темы, ошибок сети и повторного submit.

## Telegram

Никаких реальных отправок не выполнялось. Подключать только разрешённый служебный чат.

1. Ввести TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID в server env. Используется один tenant/чат через PUBLIC_TENANT_ID для первого MVP.
2. Создать случайный CRON_SECRET не короче 32 байт; хранить в server env.
3. После согласования инфраструктуры настроить GET `/api/telegram` с `Authorization: Bearer <CRON_SECRET>` по расписанию. Расписание в проект намеренно не активировано.
4. Worker добавляет due/overdue задачи на текущую московскую дату, забирает до 5 событий, таймаут одной отправки 8 секунд, до 5 попыток. Одно событие графика в день; во время теста проверить частоту, чтобы не перегружать чат.
5. Проверить успешную отправку, отказ Telegram, повторную попытку и истёкшую аренду очереди. Возможны дубли доставки при неопределённом результате; сумма платежей от этого не меняется.

## Vercel — только после подтверждения

- Framework Next.js, Node 24, build `npm run build`, output по умолчанию Next.js.
- Подключить новый приватный GitHub-репозиторий. DEMO_MODE=false.
- Разделить секреты preview/production. Для динамических preview URL задавать корректный APP_ORIGIN, не отключать Origin-проверку.
- При подключении репозитория Vercel может сразу запустить deployment: этот шаг не выполнять до разрешения пользователя.
- Применение миграций — контролируемый шаг отдельно от build. CI не меняет рабочую БД.
- После запуска smoke check: главная, вход, 401 API, RLS двух компаний, запись/отмена тестового платежа, PDF и Storage.

## Backup и восстановление

Плановые цели для согласования: RPO ≤24 часа, RTO ≤8 часов. Это цели, а не гарантии текущей версии.

- Настроить доступный backup/PITR PostgreSQL и отдельную резервную копию объектов Storage. Один SQL dump не содержит бинарные файлы Storage.
- В backup включать schema, public/private бизнес-данные и необходимые Auth/Storage метаданные согласно поддерживаемой процедуре Supabase. Ключи хранятся отдельно в менеджере секретов.
- Backup шифровать, ограничить доступ, определить срок хранения после юридического согласования. Не сохранять реальные выгрузки в Git.
- Не реже одного раза в месяц восстанавливать в закрытый staging: выполнить поддерживаемую процедуру восстановления БД и объектов, проверить UUID клиентов/Auth/tenant, RLS, суммы ledger/schedule и наличие файлов по SHA-256.
- До переключения production остановить запись, сверить журнал последних операций и не импортировать одинаковые платежи повторно. После восстановления отозвать временные доступы и проверить worker на повторные доставки.
- Откат приложения: предыдущий Git commit + совместимая версия схемы. Не откатывать миграцию удалением финансовых строк; создавать исправляющую миграцию.
